 
 -Goal-
 Given a text document and a list of entity types, extract **construct-level** entities and **evidence-local** relationships suitable for a realist-synthesis / CMOC knowledge graph.
 
 Realist shape we want (default):
 - Context (C) / Intervention (I) -> Mechanism (M) -> Outcome (O)
 - Context (C) may also directly moderate Outcome (O)
 
 -Critical constraints (strict)-
 0) The input document contains a METADATA block:
    - Between "### METADATA (IGNORE FOR ENTITY/CLAIM EXTRACTION)" and "### END_METADATA"
    - This block is for traceability only.
    - DO NOT extract entities or relationships from it.
 
 0.1) Formatting robustness (GraphRAG parsing):
    - NEVER output any special tokens like "<|DIFF_MARKER|>" or fragments like "(\"ENTITY\"".
    - NEVER include "{tuple_delimiter}" or "{record_delimiter}" inside entity names/descriptions/relationship descriptions.
    - If you cannot follow the exact output format, output nothing except {completion_delimiter}.
 
 1) Construct-level entities only (anti-noise):
    - Entities MUST be "big concepts" (phenomena/constructs), not named entities.
    - DO NOT create entities for: author names, universities/schools, journals/publishers, DOI/URLs, years, tables/figures, “the study”, “results”.
    - Avoid generic placeholders: STUDENTS, EDUCATION, LEARNING, INTERVENTION (standalone).
 
 2) Typing is mandatory:
    - Every entity MUST have a non-empty entity_type in [{entity_types}].
    - If you cannot assign a type confidently, DO NOT create that entity.
 
 3) Relationship extraction is STRICTLY CMOC-oriented:
    - Only emit relationships that fit these allowed directional families:
      * context -> mechanism
      * intervention -> mechanism
      * mechanism -> outcome
      * intervention -> outcome
      * context -> outcome
      * comparator -> outcome
    - Default rule: OUTCOME is a sink. **Never** use an OUTCOME-typed entity as the relationship source.
      (If the text truly states reverse causality, do NOT emit an edge anyway; encode it as a CLAIM later.)
 
 4) Evidence-local requirement (prevents “looks related but not supported” edges):
    - Only emit a relationship if the supporting text span is local (about 1–2 sentences) and clearly links the two constructs.
    - Relationship description MUST be ONE short causal/moderation statement (max ~20 words), using an explicit cue verb:
      increases | decreases | reduces | improves | harms | moderates | enables | inhibits | triggers | leads_to
    - Do NOT write narrative summaries (avoid “complex and multifaceted”, “research indicates”, “in summary”, etc.).
 
 -Steps-
 1) Identify entities matching the provided entity types: [{entity_types}]
 For each entity, extract:
 - entity_name: Name of the entity, capitalized
 - entity_type: One of [{entity_types}]
 - entity_description: 1–2 sentences, specific to THIS paper (mention population/setting/task if relevant)
 Format:
 ("entity"{tuple_delimiter}<entity_name>{tuple_delimiter}<entity_type>{tuple_delimiter}<entity_description>)
 
 2) Identify ONLY evidence-local relationships useful for CMOC reasoning (see allowed families and constraints above).
 For each relationship, extract:
 - source_entity (must be a previously extracted entity)
 - target_entity (must be a previously extracted entity)
 - relationship_description (ONE short causal/moderation statement with cue verb)
 - relationship_strength (1–10; higher = more explicit in text)
 Format:
 ("relationship"{tuple_delimiter}<source_entity>{tuple_delimiter}<target_entity>{tuple_delimiter}<relationship_description>{tuple_delimiter}<relationship_strength>)
 
 3) Return output in English as a single list of all entities and relationships.
 Use **{record_delimiter}** as the list delimiter.
 4) When finished, output {completion_delimiter}
